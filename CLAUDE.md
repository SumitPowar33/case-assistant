# Case Assistant – rules for every Claude session

Owner and decision-maker: Sumit Powar. Read `docs/PLAN.md` and `docs/PROGRESS.md` first, every session.

## Hard rules
- Fictional data only. Never put real names, phone numbers, accounts or case details in code, tests, fixtures or commits.
- The AI drafts; a person decides. Never build features that judge guilt, score credibility, predict who will commit crime, or use facial recognition.
- Every AI call goes through `services/ai-gateway` and is audit-logged. No direct model calls elsewhere.
- Never commit secrets. API keys and the login signing key come from environment variables (`ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `AUTH_SECRET`, `AI_AUDIT_KEY` for the gateway's keyed audit chain; the first admin from `BOOTSTRAP_ADMIN_USERNAME`/`BOOTSTRAP_ADMIN_PASSWORD`).
- Work on a branch, open a PR, never push to `master` directly.
- Run the tests before every commit; do not commit red tests.
- Commits are authored as Sumit Powar. Do not add any Claude/AI name, co-author line or session link to commits, PRs or files.

## Write the least code that works (Ponytail rule)
First read the code the change touches and trace the real flow. Then, before writing anything, go down this list and stop at the first answer that fully meets the need:
1. Does this need to exist at all? (Build only what the current task in docs/PROGRESS.md asks for.)
2. Does the codebase already have it? Reuse it.
3. Does the language's standard library handle it?
4. Does the platform handle it (Spring Boot, PostgreSQL, React, browser)?
5. Does a dependency we already have handle it? Do not add a new dependency without saying why in PROGRESS.md.
6. Can it be one line?
7. Only then write the minimum that works, plus one small test when the code has logic (a branch, loop, parser, deadline, money or security).

Never cut these to save lines: input validation at trust boundaries, error handling that prevents data loss, security and access control, audit logging, victim-identity masking, accessibility basics, or anything Sumit explicitly asked for.
No speculative abstractions, no unused options or config, no layers "for later", no copy-paste duplicates.
At the end of each session, note in PROGRESS.md anything you deliberately skipped or did not check, and any risks.

## Layout
- Login: `POST /api/login` on the core app gives an 8-hour token; the core app and the AI gateway both check it with the same `AUTH_SECRET`.
- `services/ai-gateway` – Python FastAPI. Claude + Gemini (+ offline `fake`) behind one API; per-feature provider settings; hash-chained audit log (keyed with `AI_AUDIT_KEY`, settings and audit per state; after every row the chain head goes to the core, `POST /api/ai-chain-head` signed with `AUTH_SECRET`, V35, so an older copy of the gateway's file fails the check). Every token is also checked with the core app (`CORE_URL`, `GET /api/me`; a yes is kept 30 s; core down = refused). A unit's policy `ai_cloud_allowed` = 0 (from `/api/me`) makes it refuse cloud providers. Tests: `python -m pytest -q` in that folder.
- `packages/xlit` – English-letters to Indian-script typing engine. Tests: `node packages/xlit/xlit.test.js`.
- `apps/core` – Java 21 / Spring Boot main app; Flyway migrations in `src/main/resources/db/migration`. Tests (need PostgreSQL): `mvn -f apps/core/pom.xml test` and `python -m pytest -q apps/core/db-tests`. Monthly mutation tests: `python scripts/mutate_legal_sql.py` (legal numbers in SQL), `python scripts/mutate_trigger_sql.py` (keep-as-written and masking rules in SQL) and `mvn -P mutation ... pitest-maven:mutationCoverage` (pack rule code); see `docs/TESTING.md`.
- `apps/web` – React + TypeScript (Vite). Tests: `npm test` and `npm run build` in that folder. Indian scripts are drawn with the app's own Noto Sans fonts (`@fontsource-variable/noto-sans-*`, imported in `main.tsx`, named in `index.css`); a new script needs both.
- `packs` – modules, one folder per state or the nation (`IN`): `module.json` (id, name, version, languages, depends; gives the `state_pack` row), `roles.json`, `policies.json` (a state module may add `state_values`: stricter values for its own state), `punishments.json`, `playbooks/`, `glossary.json` (legal terms in the 10 languages, `GET /api/glossary`, shown on the language tool; a draft until reviewed). Data, not code. A module may add roles, permissions and policies, never remove or loosen the national ones. Tests: `python -m pytest -q packs/tests`.
- `tests/e2e` – browser tests (Playwright, Chromium) against the real core jar, a throwaway database and the built web app: `python -m pytest -q tests/e2e`.
- `tests/repo_rules` – the hard rules of this file checked on the whole repo: `python -m pytest -q tests/repo_rules`.
- Loading existing data: CSV import in four steps for FIRs, arrests, chargesheets, evidence and notices (`ImportController`, `FirImport`, `ArrestImport`, `ChargesheetImport`, `EvidenceImport`, `NoticeImport`, V22, V24, V25, V28, V29, `packs/*/import-profiles`); design in `docs/INTEGRATION-IMPORT.md`. Insert-only, approved by a person, undoable until work is recorded.
- Front desk (module 1): `ComplaintController`, `ComplaintKinds`, V30, `packs/*/complaint-kinds.json` (golden-hour steps, draft), web `FrontDesk.tsx`. Information is written down, read over and signed (BNSS 173(1)); the signed text never changes, and an FIR registered from it (`POST /api/firs` with `complaintId`) takes it unchanged.
- Who is a protected victim (one SQL function, `identity_protected_case`, newest in V49): a victim or complainant of an FIR with BNS 64-71, BNS 124 (acid attack), IPC 376, IPC 326A/326B or any POCSO section, or an FIR flagged `sexual_offence` or `identity_protected` (set at registration from a complaint kind with `"protects_identity": true` in `complaint-kinds.json`; never cleared). Only `sexual_offence` starts the BNSS 193(2) two-month limit. Before an FIR, a complaint of a protecting kind is withheld from the desk (`ComplaintKinds.protectsIdentity`, from the pack, not a list in code).
- Reads of protected victim details are logged (`ProtectedReads`, V37, `protected_read`): any new answer that shows a protected victim's real details or the text naming them must call `ProtectedReads.fir` or `.complaints` before it is sent. The log is read on the Protected reads screen (permission `audit.read_protected`).
- Audit log (`AuditLog`, `GET /api/audit-log?stationId=`, web `AuditPage.tsx`, screen `#/audit`): one read-only list for a station of the protected reads, accepted readiness gaps (and withdrawals) and admin changes, for whoever holds `audit.read_protected` there. The AI's own audit stays in the gateway and is not in it yet.
- Statements under BNSS 180 (`StatementController`, V40, web `Statements.tsx`): kept as said in the language spoken, never changed; the tracker is read from the case's people; reads of a protected case's statements are logged (`statements`).
- AI translation of a statement (A3, board 6, `statementTranslate.ts`, `Statements.tsx` `Translation`, `POST /api/firs/{id}/statements/{sid}/translation`, V52 `statement_translation`): the gateway (`statement_translate`) drafts English for a statement made in another language; the browser lists the original's numbers (any Indian script's digits) the draft lacks; the officer corrects and saves it as checked (kept as written, once, with the AI's draft and request), or rejects it; the decision is logged. It sits under the original, never in its place. Not for English, a protected case or a masked person (web, API and a trigger).
- Money trail (`MoneyTrailController`, V42, web `MoneyTrail.tsx`): transfers and bank holds typed from bank replies in the evidence register, kept as written; the table of the accused reads the money that reached each one next to the existing account-holder marks and `accused_link` rows (readiness check, V6). Money alone is never shown as proof; no score.
- Case property register (`PropertyController`, `GET /api/property`, V43 `custody_event.place`, web `Property.tsx`, screen `#/property`): the seized physical items of the cases the caller may open (case team, `fir.read_station`, or `evidence.custody` at the FIR's station) with where each is by its newest hand-over (malkhana, lab or court, back to the owner); hand-overs are added with the existing `POST /api/firs/{id}/evidence/{itemId}/custody`, which now takes an optional `place`. The log is append-only. QR labels and scanning (board 15) are not built.
- Court and trial tracker (`CourtController`, `GET /api/court`, `GET /api/firs/{id}/court`, V45 `court_event` and `court_summons`, web `Court.tsx`, screen `#/court`): the court dates of a case (past and coming; the next date is the earliest coming one) and the summons to each witness (newest step per witness is current); rows are kept as written; writing is for the case team. No ICJS feed, no AI brief.
- Search and seizure memo (`SearchController`, `GET/POST /api/firs/{id}/searches`, `POST .../{searchId}/forwarded`, V48, web `Search.tsx`, FIR part `search`, board 7): written once the search is over and frozen on saving, in one request (nothing kept on the device); grounds (BNSS 185(1)), two witnesses or the reason (103(4)), at least one recording's SHA-256 and length (105; the file stays in e-Sakshya), sealed items become evidence items with `search_id`; the day the recording went to the Magistrate, once. Case team only. No photos, selfie, QR or offline sync.
- AI fact check of the FIR text (A1, board 2, `FactCheck.tsx`, `factCheck.ts`, `FactController`, `GET/POST /api/firs/{id}/facts`, V50 `fir_fact`): the gateway (`fir_extract`) lists dates, times, places, amounts and the numbers of accounts, phones, UTRs and UPI ids, never names; the browser shows only facts whose quote is words of the FIR text (a number must be in its quote); the officer confirms (or corrects) each, and only then is it kept as written with its quote (the database refuses a quote not in the text); finishing logs the decision in the gateway. Case team only; not offered on a protected case (its text would leave for the AI provider); a protected case's facts are read as its text (`ProtectedReads`).
- AI section suggestion (A2, `SectionSuggest.tsx`, `sectionSuggest.ts`, `SectionController`, `GET/POST /api/firs/{id}/sections`, V51): the gateway (`section_suggest`) reads the FIR text against the charges of `packs/*/playbooks` and says which ingredients the text may describe, quoting it; the browser shows a charge only with the playbook's own ingredient texts and quotes that are words of the FIR text; the officer adds it with a reason (10+ characters), kept as written in `fir_section` with who, when, why and the gateway request (the readiness check, deadlines and masking read it as any section); finishing logs the decision. A section is added only from a playbook charge, and only of the law the offence falls under (`fir_offence_law`: BNS from 1 July 2024 India time, IPC before; a trigger refuses the other). Case team only; not offered on a protected case.
- AI draft of the final report's narrative (A6, board 10, `chargesheetDraft.ts`, `NarrativeDraft.tsx` on the Final report part, V54 `final_report_event.ai_request`): the gateway (`chargesheet_draft`) drafts the facts in brief and the evidence one sentence at a time from the FIR text and the statements (with their checked English translations, never a masked person's), each naming its piece and quoting it; the browser shows a sentence only when its quote is words of that piece, and never one that judges guilt, truthfulness or proof (`judges`); the officer ticks sentences, they are added after the officer's own words with their source in brackets, the decision is logged in the gateway, and the save names the request (shown in the report's steps). Not offered on a protected case.
- Old law to new law finder (`LawFinder`, `GET /api/law-finder`, data `packs/*/law-concordance.json` `sections`: law IPC/CrPC/IEA, old, new or null, what, optional partial; web `LawFinder.tsx`, screen `#/laws`): a look-up table for any signed-in officer, a draft until a prosecutor has checked it; never converts a section (`FirImport` reads the IPC rows of the same file as a hint). No AI explanation yet.
- Acting charge (`ActingChargeController`, V53 `acting_charge` and `acting_charge_end`, permissions `acting.grant` (SP, state admin) and `acting.allowed` (the role that may be held, `sho`) in `packs/IN/roles.json`): an officer posted at a station holds a temporary role (BNSS 2(1)(r)), given by a holder of `acting.grant` in reach of the station with a reason and a last day at most 90 days away (India date), ended by itself after that day or early with a reason; never to oneself; kept as written and in the admin log (`acting_started`, `acting_ended`, so the Audit screen shows both). Access follows it through `CaseTeam.holds` (SQL) and `CaseTeam.activeRoles` (Java): case reach, `can`, `canAt`, policy rights and `/api/me` (`permissions`, `case_scope`, `acting`). Also followed (session 89): choosing the acting officer as IO (`CaseTeam.canBeIo`, the IO candidate lists, the import's IO lookup) and `fir.register` at the station (`canRegisterAt`).
- Demo: `scripts/demo_case.py` loads one fictional station (MH) and one online-fraud case through the API; `docs/DEMO.md` is the demo script; `tests/e2e/test_demo_case.py` loads it on every run.
- Hardening (security review, 2 Nov 2026): request bodies are capped (`BodyLimit`: 1 MiB, 16 MiB for an import); an error never shows SQL or a Java message (`ApiErrors`); passwords are at most 72 bytes (bcrypt); the gateway takes plain model names only and 20 drafts per officer in 10 minutes; the built web page carries a Content-Security-Policy (`vite.config.ts`, checked by `tests/e2e/test_content_policy.py`). Every token has an id; `POST /api/logout` ends it (V38 `signed_out_token`); 30 wrong passwords from one address lock that address for 15 minutes; the installation's web server is `deploy/nginx.conf` (HTTPS, headers, forwarded address; `tests/repo_rules/test_deploy_config.py`, `tests/e2e/test_https_proxy.py`). Keep them when adding routes or fields.
- `docs/` – plan, progress, research, `ARCHITECTURE-TENANCY.md` (accounts, roles, policies, modules: read before touching access), `TESTING.md` (what every change must test).

## Testing rule (Sumit, 28 Oct 2026)
Every piece of code gets tests (unit, functional, database, security as `docs/TESTING.md` lists), and **the whole suite runs every day**: `scripts/test-all.sh` (add `--no-db` only when PostgreSQL cannot start; say so in PROGRESS.md). Run it before you start (baseline) and before every commit. Coverage gates (core 96/90, web 97/89, gateway 97) may only go up. A bug gets a regression test first. A new route is covered by `SecurityMatrixTest`; list it there if it is public or admin-only.

## Who may see and do what
Case access comes from the role's data in `packs/*/roles.json` (case team = the named IO while posted at the FIR's station, plus roles scoped to the station or district; a moved IO's open FIRs wait on the Supervisor review's "IO has left the station" list). A state admin works only inside their own state; an admin without a station is the platform admin. A state, district or station may only tighten a policy (`policies.json`), never loosen what is above it. Do not hard-code role names in new code: use a permission from `roles.json`.
